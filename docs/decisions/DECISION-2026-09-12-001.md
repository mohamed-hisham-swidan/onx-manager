# DECISION-2026-09-12-001 — Redefine Phase 4 Feature 1 as a standalone git/CI-CD-inspired versioning & test system

**Status:** Accepted  
**Lane:** B (Release Improvement) — this is the product's stated core competitive differentiator, not a launch blocker, but materially defines release value  
**Decision level:** D2 (Major — changes architecture, technology direction, creates a new subsystem, substantial maintenance cost)  
**Roadmap drift:** Controlled  

---

## Context

ROADMAP_v1.1 Phase 4, Feature 1 was originally scoped as "Transparent update system (rollback/proceed/disable + failed-mod list)" — a bounded feature confirmed by both the original r/admincraft research (2026-08-10) and a follow-up deep-research pass (2026-09-12, 10-theme analysis, primarily r/admincraft + GitHub issues on Pterodactyl/AMP/Crafty) as the single highest-pain-point area for Minecraft server admins.

The deep-research pass additionally surfaced that:
- No existing tool in this space (Pterodactyl, AMP, Crafty Controller, Packwiz, itzg/docker-minecraft-server, Borg/Restic/bup) provides native branch/stage concepts, one-click server cloning for testing, or automated sandbox testing before production updates.
- Naive git-on-the-server-directory approaches fail in practice due to binary churn from region files, JARs, and database files (Theme 6), forcing communities into unnatural config-only-repo splitting.
- The strongest-evidenced design direction (the research's own Tier 1 synthesis) is a **decoupled architecture**: versioned config/mod manifests treated like commits, separated from mutable world/DB state treated as snapshotted volumes, with isolated ephemeral test containers and atomic rollback.

Mohamed's direction (2026-09-12 session): rather than build the bounded "rollback/proceed/disable" feature as originally scoped, build this into the project's core competitive differentiator — a git-inspired system for Minecraft servers (branches, commits, isolated per-test containers), with groundwork laid for an eventual multi-node capability (running a test instance on a separate node; future resource-distribution). This also comes with an intent to reorganize/refactor related parts of the UI as this system lands.

A codebase audit pass against the 5 original Phase 4 features (baseline: Phase 5 closed, commit 183ae7b, 3,159 tests, 5/5 CI gates) confirmed **zero existing code, aggregates, or scaffolding** anywhere in the repo related to branching, commits, git-like versioning, or multi-node — this is new scope, not an extension of anything already underway. The codebase audit did confirm strong natural dependency links from the original Feature 5 (crash/log parsing) and Feature 3 (mod-folder targeting) into what was Feature 1 — those links remain relevant and should inform (but not dictate) the new system's design.

## Evidence

- Mohamed's explicit directive (2026-09-12 session): this is described as the project's "dream," core goal, and only real competitive edge — not an incremental feature.
- Original r/admincraft research (2026-08-10): update-cycle trust and lack of pre-production testing is the dominant pain point by wide margin.
- Deep-research pass (2026-09-12): 10-theme, multi-source analysis (r/admincraft threads 2021–2026, GitHub issues on pterodactyl/panel #2148/#2250 open since 2020, etc.) confirms no existing tool solves this well, and independently arrives at a decoupled-versioning + ephemeral-test-container architecture as the strongest-evidenced direction.
- codebase audit (2026-09-12, corrected re-run): confirmed no existing implementation conflicts with or partially covers this new scope; confirmed related features (crash parsing, mod management, change history) have natural, non-blocking dependency links into it.

## Options considered

1. **Keep Feature 1 as originally scoped** (bounded rollback/proceed/disable, per the rejected first-pass Design Spec's Batch 4) — rejected. Would ship a materially smaller feature than what Mohamed has identified as the project's actual differentiator, and would likely require significant rework later to retrofit branching/versioning concepts onto a narrower design.
2. **Build the full git/CI-CD-inspired system now as the redefined Feature 1**, as a standalone subsystem (not layered on the existing DockerProvider/ServerProvider abstraction used for production servers) — accepted.
3. *(Not selected, noted for completeness)* Build the bounded feature first as a stepping stone, then expand later — rejected per Mohamed's explicit preference to commit to the larger vision now rather than incrementally.

## Decision

Phase 4, Feature 1 in ROADMAP_v1.1 is redefined from "Transparent update system" to: **a git-inspired versioning and isolated-testing system for Minecraft servers** — supporting branch-like and commit-like tracking of server state, isolated per-test containers for trialing changes before promotion, and architectural groundwork for a future multi-node testing/resource-distribution capability (multi-node execution itself remains out of scope for the initial build — see Impact below).

This system will be built as a **standalone subsystem, architecturally separate from the existing production-server `ServerProvider` abstraction** (`LocalLinuxProvider` / `LocalWindowsProvider` / `DockerProvider` from Phase 5). It does not extend or wrap those providers. Production server lifecycle management is unaffected by this decision.

Phase numbering and overall roadmap order (Phase 4 position, features 2–5 unchanged in scope) are **not** affected by this record — only Feature 1's internal definition changes. Features 2–5 retain their audited scope from the 2026-09-12 codebase audit pass pending their own Design Specs.

The original bounded scope items (failed-mod list, rollback, proceed, disable) are **not dropped** — they become use cases realized through the new system's branch/commit/test-container primitives, rather than a separate bespoke mechanism.

## Impact

- **Product/user:** Feature 1 becomes substantially larger in user-facing surface area (new mental model: branches/commits for a game server, not just an update dialog). Likely increases Phase 4 Feature 1's timeline materially versus the original bounded scope.
- **Architecture:** Introduces a new subsystem with its own state model (config/mod manifests as versioned "commits", world/DB state as separate snapshot/volume tracking) and its own isolated container execution path, deliberately decoupled from the existing `ServerProvider` hierarchy. This is new architectural surface, not a refactor of Phase 5's work.
- **Multi-node groundwork:** The initial build lays architectural groundwork (e.g., keeping execution-target selection abstracted) but does **not** implement actual multi-node orchestration in this decision's scope — that remains a distinct future capability, to be scoped separately when reached.
- **UI:** Mohamed has signaled an intent to reorganize/refactor related UI areas as this lands — exact scope of that refactor is not yet defined and should be captured in the Design Spec, not assumed here.
- **Storage/infra dependency (open, not yet decided):** The evidence-strongest design pattern found in research (atomic copy-on-write snapshots) implies a filesystem/storage-driver dependency (e.g., ZFS, Btrfs, or Docker overlay driver) not currently confirmed as available or required on target deployment environments. This is an open codebase audit item, not decided by this record.
- **Governance:** Per project governance standards("why now?"), the justification is that this is explicitly the project's core release-relevant differentiator per the project owner, materially improving release value — an acceptable answer under the "why now" test, distinct from a "would be cool" justification.

## Effort

Not yet estimated — pending a dedicated codebase audit pass on storage-layer feasibility (COW snapshot support on target platforms) and a full Design Spec. Expected to be materially larger than the original bounded Feature 1 scope; likely warrants its own batch structure similar to Phase 5's.

## Reversibility

Moderate. Because the new system is architecturally standalone (not wrapping/extending the existing `ServerProvider` hierarchy), no changes to Phase 5's shipped work are required to build it, and no changes to it would be required to revert this decision — reversal would mean discarding the new subsystem's code, not unwinding changes to production server management. However, once real usage/data exists inside the new system (branches, commits, test history), reversal cost rises accordingly.

## Roadmap impact

Moderate — Feature 1's definition changes materially; phase numbering, phase order, and Features 2–5 scope are unchanged. `ROADMAP_v1.1.md` should be updated to reflect this record's redefinition of Feature 1 once the Design Spec locks initial scope boundaries.
