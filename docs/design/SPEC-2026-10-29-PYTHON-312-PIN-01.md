## 1. Decision Record (D1)

### 1.1 Problem

The installers currently resolve "any Python newer than 3.12", not Python 3.12. That
allows a host with only Python 3.13/3.14 to be accepted silently, even though the
project's own tooling and dependency set are only exercised on 3.12. The concrete
evidence at HEAD `d1a6d2d`, re-checked against the post-B0 `start.ps1` (554 lines):

- `start.ps1:413-418` probes `py -3.13` and `python3.13` **before** the 3.12 candidates.
- `start.ps1:417-418` accepts any `python3`/`python` with `sys.version_info >= (3,)`.
- `start.ps1:402-410` reuses `backend/.venv` with **no version check at all**.
- `start.ps1:451` installs `Python.Python.3.12`, but `:455` then sets
  `$foundCmd = 'python'` without re-probing; `:485` and `:490-491` do the same for the
  python.org installer path.
- `start.sh:16-21` reuses the venv when `sys.version_info >= (3, 12)`.
- `start.sh:25-32` prefers `python3.13` over `python3.12`.
- `start.sh:47-65` installs **unversioned** `python3`/`python` via apt/dnf/pacman.
- `start.sh:75-81` accepts any `>= 3.12` at the final gate.
- `launcher.py:1675-1691` (`check_python`) rejects only `< 3.12`.
- `launcher.py:2285-2298` (`is_valid_python`) accepts any `>= 3.12`.
- `launcher.py:2301-2332` (`find_system_python`) prefers `Python313` paths.
- `launcher.py:2633-2673` (`ensure_python_environment`) reuses any valid venv and has
  no recreate path.
- `scripts/bootstrap:9` creates the venv with bare `python3`.
- Docs still advertise 3.14 or mix "3.12+" with "3.12": `docs/getting-started.md:7`,
  `docs/DEVELOPMENT.md:5`, `docs/architecture/SPECS.md:26,30`,
  `docs/architecture/ARCHITECTURE.md:177`, `docs/CONTRIBUTING.md:22`, and
  `README.md:9,83,102` ("3.12+") vs `README.md:128` ("3.12").

`start.ps1` and `start.sh` run **before** `launcher.py`, so they cannot delegate the
interpreter decision to it. The same rule must therefore exist independently in all
three entry points and in `scripts/bootstrap`.

### 1.2 Decision

Pin **major.minor exactly to `(3, 12)`** everywhere an installer or bootstrap script
chooses an interpreter:

1. Accept only `sys.version_info[:2] == (3, 12)`. Any 3.12.x patch is valid.
2. If 3.12 is absent, install 3.12. Never fall back to 3.11, 3.13, or 3.14.
3. If `backend/.venv` is not exactly 3.12, delete it and recreate it automatically with
   3.12. No backup (there are no users yet). Deleting is permitted only after the
   safe-delete guard in §5.4 (deletion only in launcher.py; §5.4) passes.
4. `backend/pyproject.toml` `requires-python = ">=3.12"` is **not** changed in this
   batch. The pin is an installer/runtime-resolution policy, not a package-metadata
   change.
5. `start.ps1` keeps its UTF-8 BOM.
6. `start.sh` is a bash script (`#!/usr/bin/env bash`) and stays bash-compatible, not
   POSIX-sh. Python lines stay within 100 characters
   (`scripts/check-ruff-baseline`).

There is no packaged binary artifact in this repository after B0; every launcher path
resolves a source interpreter and is therefore covered by this pin.

### 1.3 Alternatives rejected

| Alternative | Why rejected |
|---|---|
| Keep `>= 3.12` and merely warn on 3.13/3.14 | A warning is still a silent success; the requirement is that the installers never use 3.13/3.14. |
| Prefer newest Python (3.13/3.14) for performance | The project is only verified on 3.12; the dependency set and test suite are the contract. |
| Reuse a 3.13 venv and install dependencies into it | It hides the drift and defeats the pin; owner decision 2 requires recreation. |
| Change `requires-python` to `==3.12.*` | Explicitly out of scope (owner decision 3); package metadata is a separate decision. |
| Let `launcher.py` decide and make `start.*` a thin wrapper | `start.ps1`/`start.sh` execute first and must select/install an interpreter before `launcher.py` can run. |
| Delete `backend/.venv` without a guard | Dangerous if a user or symlink points `.venv` elsewhere; could delete unrelated data. |
| Install unversioned distro `python3` and hope it is 3.12 | This is the current bug: on CachyOS/Arch and many rolling distros, `python` is 3.13/3.14. |
| Auto-bootstrap `uv` with a remote install script | Supply-chain risk; see §5.3 and decision Q1 in §12. |

### 1.4 Consequences

Positive:

- A host with only 3.13/3.14 gets 3.12 installed instead of a broken or untested run.
- A stale 3.13 venv is repaired automatically.
- One pinned constant per file makes future patch bumps auditable.
- Docs stop advertising an unsupported runtime.

Negative / accepted:

- Installing Python is slower on first run and may prompt for `sudo` on Linux.
- On distros without a versioned 3.12 package (CachyOS/Arch is the known risk), the
  Linux path may stop and ask the user to install `uv` or 3.12 manually.
- `requires-python = ">=3.12"` still lets `pip`/`ruff` run under 3.14 if invoked
  directly. Only the installers are pinned in this batch.
- There is no prebuilt binary path after B0, so there is no binary that can bypass the
  source pin; the source resolver is the only entry path.

## 4. Design — One Constant per File

### 4.1 `launcher.py`

```python
PINNED_PYTHON: tuple[int, int] = (3, 12)
PINNED_PYTHON_DISPLAY = "3.12"
PYTHON_INSTALLER_VERSION = "3.12.8"
PYTHON_INSTALLER_URL = (
    f"https://www.python.org/ftp/python/{PYTHON_INSTALLER_VERSION}/"
    f"python-{PYTHON_INSTALLER_VERSION}-amd64.exe"
)
```

Every predicate uses `sys.version_info[:2] == PINNED_PYTHON`. No `>=` comparison for
the pin remains in the interpreter-selection path. Installer path/name and URL are
derived from `PYTHON_INSTALLER_VERSION`; the literal `3.12.4` and the second `3.12.8`
literal disappear.

### 4.2 `start.ps1` (BOM preserved)

```powershell
$PinnedPythonMinor = '3.12'
$PythonExactProbe = 'import sys; sys.exit(0 if sys.version_info[:2] == (3,12) else 1)'
$PythonVersionProbe = 'import sys; print(sys.executable)'
```

`$PythonExactProbe` is used for every candidate. `$PythonVersionProbe` is used after
installation to obtain the **absolute** interpreter path.

### 4.3 `start.sh`

```bash
PINNED_PYTHON="3.12"
PYTHON_EXACT_PROBE='import sys; sys.exit(0 if sys.version_info[:2] == (3,12) else 1)'
PYTHON_EXEC_PROBE='import sys; print(sys.executable)'
```

### 4.4 `scripts/bootstrap`

```bash
PINNED_PYTHON="3.12"
PYTHON_EXACT_PROBE='import sys; sys.exit(0 if sys.version_info[:2] == (3,12) else 1)'
```

### 4.5 Installer version unification

Use **3.12.8** as the single python.org patch version. `launcher.py:2429,2432` already
uses 3.12.8; `start.ps1:459-460` currently uses 3.12.4 and must change to 3.12.8.
Winget remains the primary Windows path (`Python.Python.3.12`). The python.org 3.12.8
release page (`https://www.python.org/downloads/release/python-3128`) states that the
Windows binaries' code-signing certificates were revoked, so the `.exe` may fail to
download, install, or run; this is why winget is first. The URL itself exists
(owner-verified 2026-10-29). See decision Q2 in §12 and R1.

## 5. Resolver Algorithms

### 5.1 Windows (`start.ps1`, then `launcher.py`)

Ordered steps. Stop at the first exact-3.12 interpreter and record its **absolute**
path.

1. **Existing venv** — if `backend\.venv\Scripts\python.exe` exists:
   If the exact probe passes, use it. If it fails, leave it untouched and continue to interpreter resolution. start.sh / start.ps1 never delete or modify backend/.venv; launcher.py performs any stale-venv removal later (see launcher section).
2. **`py -3.12`** — probe `py -3.12 $PythonExactProbe`. On success run
   `py -3.12 $PythonVersionProbe` and store the printed `sys.executable`.
3. **`python3.12`** — same exact probe; store `command -v` / `where.exe` absolute path.
4. **`py` (no selector)** — exact probe only; accepted only if it reports
   `(3, 12)`. This catches installs whose launcher default is 3.12.
5. **`python3` and `python`** — exact probe only; accepted only if `(3, 12)`.
6. **winget (primary install path)** —
   `winget install Python.Python.3.12 -e --silent --accept-source-agreements
   --accept-package-agreements`.
7. **python.org installer (fallback)** — download `$PYTHON_INSTALLER_URL`, run
   `/quiet InstallAllUsers=0 PrependPath=1 Include_test=0` **per-user first**; if that
   fails, retry system-wide with `InstallAllUsers=1`. This matches decision Q5 and
   `launcher.py`'s current per-user behavior (`launcher.py:2445-2455`). The current
   `start.ps1` order is the reverse (`start.ps1:468-483`) and B3 changes it.
8. **Re-probe (mandatory)** — after winget or python.org install, refresh `$env:Path`
   by re-reading the Machine and User `Path` values from the registry (for example
   `[Environment]::GetEnvironmentVariable('Path','Machine')` and
   `...('Path','User')`), then probe, in order, these absolute paths:
   - `%LOCALAPPDATA%\Programs\Python\Python312\python.exe`
   - `%ProgramFiles%\Python312\python.exe`
   - `%ProgramFiles(x86)%\Python312\python.exe`
   - `C:\Python312\python.exe`
   - `py -3.12 -c "import sys; print(sys.executable)"`
   - `python3.12 -c "import sys; print(sys.executable)"`
   Every probe must pass `$PythonExactProbe`. The first passing absolute path becomes
   `$pyBin`. Absolute-path probing remains the source of truth; the PATH refresh is
   only a convenience. Never set `$foundCmd = 'python'` after an install.
9. **STOP** — if no exact 3.12 is found, throw:
   `"Python 3.12.x was not found or could not be installed. onx-manager requires
   exactly Python 3.12; 3.13/3.14 are not supported. Install Python 3.12 from
   python.org, then re-run start.bat."`

`launcher.py` mirrors steps 2-9 through `find_system_python()` and
`auto_install_python_windows()`; both use the same exact predicate, the same installer
constant, and the same per-user-first install order. `find_system_python()` drops the
`Python313` entries and searches `Python312` only. `launcher.py`'s equivalent STOP
messages are the same verbatim Windows text above (in
`auto_install_python_windows()`) and the same verbatim POSIX text in §5.2 step 8 (in
`install_python_posix()`).

### 5.2 Linux / macOS (`start.sh`, then `launcher.py`)

Ordered steps. Stop at the first exact-3.12 interpreter.

1. **Existing venv** — If the exact probe passes, use it. If it fails, leave it untouched and continue to interpreter resolution. start.sh / start.ps1 never delete or modify backend/.venv; launcher.py performs any stale-venv removal later (see launcher section).
2. **`python3.12`** on `PATH` — exact probe; store `command -v python3.12`.
3. **`python3` / `python`** — exact probe only; accepted only if `(3, 12)`.
4. **uv** — if `uv` is present:
   - `uv python install 3.12`
   - `uv python find 3.12`
   - Verify the returned path with the exact probe; otherwise continue.
5. **apt** (versioned only: `sudo apt-get update && sudo apt-get install -y python3.12 python3.12-venv`, probe `python3.12`).
6. **dnf** (versioned only: `sudo dnf install -y python3.12`, probe `python3.12`).
7. **Homebrew** (`brew install python@3.12`, probe `$(brew --prefix python@3.12)/bin/python3.12`, only when the prefix is non-empty).

   Never run `apt-get install python3`, `dnf install python3`, or `pacman -S python`; `start.sh` has no Python pacman branch.

8. **STOP** — print and exit 1:
   `"Python 3.12.x is required. onx-manager does not support Python 3.13/3.14.
   Install Python 3.12 with one of: 'uv python install 3.12' (recommended),
   'brew install python@3.12' (macOS), or your distro's python3.12 package, then
   re-run ./start.sh."`

`launcher.py` adds a POSIX install path as `install_python_posix()` so a direct `launcher.py` invocation does not silently rely on `start.sh`. Its order differs from the `start.sh` order above: `launcher.py` uses uv > Homebrew > versioned apt > versioned dnf (launcher.py:2790-2897), while `start.sh` uses uv > apt > dnf > Homebrew. Neither installs an unversioned `python3`, and `launcher.py` ends with the same verbatim STOP text as step 8. Unifying the two orders is future work (see B6 follow-ups); do NOT change launcher.py as part of B5.

### 5.3 Should `start.sh` bootstrap `uv` itself if absent?

**Decision (Q1, answered 2026-10-29): no, not in this batch.** Auto-installing `uv`
would require piping a remote script to a shell (or trusting an unpinned remote
binary), which is a supply-chain decision larger than this pin. If `uv` is absent, the
resolver tries Homebrew and explicit versioned distro packages, then stops with manual
instructions. If none works, the STOP text tells the user exactly how to install
Python 3.12 for the project and re-run the installer. This keeps the failure explicit
and lets the owner decide later. The launcher failure paths in `launcher.py`
(`validate_startup_prerequisites` at `:2884-2890` and `start_backend` at `:3573`) use
these same platform-selected STOP texts (verbatim §5.1 step 9 on Windows, verbatim §5.2
step 8 on Linux/macOS) via `sys.platform`, ensuring no bare `python -m venv` or stale
`"3.12+"` messages are emitted.

### 5.4 Safe-delete guard for `backend/.venv`

The guard is launcher.py only; start.sh and start.ps1 never delete backend/.venv. It must:

0. **No-op when `backend/.venv` does not exist** — return immediately; there is
   nothing to delete.
1. Resolve the repository root and construct `expected = <repo>/backend/.venv`.
2. Refuse if `backend/.venv` is a symlink (`Path.is_symlink()`) or a Windows junction
   (`Path.is_junction()`, available on Python 3.12).
3. Resolve the real path (`Path.resolve()` / `os.path.realpath`) and require exact
   equality with `expected.resolve()`.
4. Require the resolved parent to be exactly `<repo>/backend`.
5. Only then delete the resolved path (`shutil.rmtree` on Python).
6. On any guard failure or deletion error, **stop** with a clear message. Do not fall
   back to the stale venv and do not continue with a different interpreter.

Reference Python implementation:

```python
def _venv_removal_target() -> Path | None:
    if not VENV_DIR.exists():
        return None  # no-op: nothing to delete
    repo_root = PROJECT_ROOT.resolve()
    expected = repo_root / "backend" / ".venv"
    if VENV_DIR.is_symlink() or VENV_DIR.is_junction():
        raise ValidationError(
            "Refusing to delete backend/.venv: it is a symlink or junction.",
            "Remove it manually, then re-run the launcher.",
        )
    actual = VENV_DIR.resolve()
    if actual != expected.resolve() or actual.parent != repo_root / "backend":
        raise ValidationError(
            f"Refusing to delete unexpected path: {actual}",
            f"Expected {expected}. Remove it manually, then re-run the launcher.",
        )
    return actual
```

## 6. `launcher.py` Behavior

### 6.1 Started by a non-3.12 interpreter (`check_python`)

`Validator.check_python()` (`launcher.py:1675-1691`) changes from "reject `< 3.12`" to
`sys.version_info[:2] != (3, 12)` and raises `ValidationError` before any service
starts. Exact text:

- Message: `"Python {ver} is not supported: onx-manager requires exactly Python 3.12.x
  (3.13 and 3.14 are not supported)."`
- Fix: `"Run start.ps1 (Windows) or start.sh (Linux/macOS) so Python 3.12 is installed
  and selected, or invoke launcher.py with a Python 3.12 interpreter."`

`validate_startup_prerequisites` (`launcher.py:2871-2897`) already calls
`ensure_python_environment()` first and then `check_python()`. The order is kept.
In the normal path, `start.ps1`/`start.sh` run `launcher.py` with the venv interpreter
(`$pyBin` on Windows, the venv `python` on POSIX), so the launcher interpreter is the
pinned 3.12 in the normal path, and no frozen build exists anymore. Consequences:

- If `launcher.py` is run as `python3.13 launcher.py`, `ensure_python_environment()`
  may create a valid 3.12 venv, but `check_python()` still sees the **current**
  process interpreter (3.13) and fails. The launcher does **not** re-exec itself in
  this batch; the user is told to use `start.sh`/`start.ps1` or a 3.12 interpreter.
  This is deliberate: silent re-exec hides which interpreter the user invoked.
- If `launcher.py` is run under 3.12, behavior is unchanged.
- `check_python()` returns the current version and the venv path as before.

### 6.2 Existing venv that is not 3.12

`ensure_python_environment()` (`launcher.py:2633-2673`) becomes:

1. `find_backend_venv()`.
2. If a venv exists and `is_valid_python()` is true, return it.
3. If a venv exists and is not exact 3.12, run the guard (§5.4), remove it, log
   `"Removing backend/.venv (Python <ver> is not 3.12)."`, and continue.
4. `find_system_python()`; on Windows, `auto_install_python_windows()` if absent; on
   POSIX, `install_python_posix()` if absent.
5. Create the venv with the exact 3.12 absolute path.
6. Re-run `find_backend_venv()` + `is_valid_python()`; if the new venv is not exact
   3.12, remove it and return `None` with a clear error. Never return a wrong-version
   venv.

When `ensure_python_environment()` returns `None`, callers in `launcher.py` invoke
`ErrorHandler.show(...)`:
- In `validate_startup_prerequisites` (`launcher.py:2882-2890`): `if python is None: ErrorHandler.show(...)`.
- In `start_backend` (`launcher.py:3565-3580`): `if python is None: python = ensure_python_environment(); if python is None: PIDManager.clear_active_port(); _clear_backend_pid_if(None); ErrorHandler.show(...)`.

Both `ErrorHandler.show` occurrences and `Validator.check_python` (`launcher.py:1681-1682`)
are rewritten so that none says `"3.12+"` or suggests running bare
`cd {BACKEND_DIR} && python -m venv .venv`. Instead, they display the verbatim STOP
equivalents selected by `sys.platform`:
- Windows (`sys.platform == "win32"`): §5.1 step 9 verbatim STOP text:
  `"Python 3.12.x was not found or could not be installed. onx-manager requires exactly Python 3.12; 3.13/3.14 are not supported. Install Python 3.12 from python.org, then re-run start.bat."`
- Linux / macOS (`sys.platform != "win32"`): §5.2 step 8 verbatim STOP text:
  `"Python 3.12.x is required. onx-manager does not support Python 3.13/3.14. Install Python 3.12 with one of: 'uv python install 3.12' (recommended), 'brew install python@3.12' (macOS), or your distro's python3.12 package, then re-run ./start.sh."`

Additionally, docstrings and comments at `launcher.py:2286` (`is_valid_python`),
`launcher.py:2302` (`find_system_python`), `launcher.py:2634` (`ensure_python_environment`),
and `launcher.py:2721` (wheel replacement comment) are reworded from `"3.12+"` to `"3.12"`.

## 12. Decisions (answered 2026-10-29)

| ID | Question | Decision |
|---|---|---|
| Q1 | May `start.sh` auto-bootstrap `uv` when it is absent? | **No.** `start.sh` does not auto-install `uv`. Use the other install methods; if none works, STOP with a clear message that tells the user how to install Python 3.12 for the project and re-run the installer.
